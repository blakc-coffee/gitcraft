# Beginner-flow revision

User finding: the original workbench displayed too much information and assumed command knowledge. The revision removes the initial workbench, teaches file editing before staging/committing, and splits collaboration into receiving, combining and sharing. Commands are explained before execution; buttons and optional typing use the same native Git gateway. Help never costs an attempt or progress.

The frontend, design-taste and product-design-quality skills were already installed. No download, framework migration or third-party dependency was needed. Taste guidance was applied proportionally to hierarchy, density, typography, copy, accessibility and states; landing-page patterns do not govern this multistep product flow.

Reference principles: [GOV.UK question pages](https://design-system.service.gov.uk/patterns/question-pages/) for focused tasks; [WAI multi-page forms](https://www.w3.org/WAI/tutorials/forms/multi-page/) for logical steps and progress; [WAI notifications](https://www.w3.org/WAI/tutorials/forms/notifications/) for concise feedback and recovery. These support interface choices, not a claim of validated teaching efficacy. No GOV.UK package or visual identity is imitated.

Automated coverage includes separate edit/stage/commit milestones, fetch versus integration/share, safe progress restoration, explanatory step metadata, and preserving native repositories across lesson switching. The existing Git correctness and HTTP boundary checks remain in force.

Verification completed: 17 Python engine/HTTP tests and five JavaScript lesson tests passed, plus JavaScript syntax checks. Both guided lessons were completed through browser controls using real Git. An invalid time retained its step and exposed the filled-example helper; a mistyped command retained the typed text and step. Returning to a prior lesson and refreshing retained progress. Focus recovery was added for rejected typed commands. Heading focus and keyboard access were checked through the flow. Screen-reader testing and observation with actual first-time learners have not been performed.

Normal-view and narrow-view screenshots are `.impeccable/review/beginner-preview.png` and `beginner-mobile.png`. The first mobile capture exposed a low primary button; tighter spacing and a shorter opening put its bottom at about 559 CSS pixels in a 670-pixel-high test viewport, with no horizontal document overflow. Native screenshots were used after full-page captures with viewport overrides proved clipped. The viewport override was reset and the normal local preview left at a fresh introductory lesson. Light/dark colors are implemented through system preference; the browser's dark preference was inspected visually. No Lighthouse or complete automated accessibility audit was run.

Product boundary: this is introductory guided practice. A complete zero-to-independent course still needs terminal orientation, branch/conflict/recovery lessons and independent transfer assessment. Completion is not labeled mastery. Representative novice observation remains necessary before claiming the flow works for every beginner.

## Terminal-led revision
The user's correction is that Git execution and learning must remain the core activity. The terminal now stays open under a smaller editor, with a terminal focus view. README opens first so code boilerplate does not dominate. The intent guide explains commands; helper actions only suggest editable commands and never submit them. Enter/Run submits the native-Git request. The response transcript is per workspace, command recall uses up/down arrows, errors preserve the submitted text, and state summaries distinguish staged/unstaged changes. The browser prototype uses the existing real local Git repositories and a bounded gateway, not an unrestricted shell.
